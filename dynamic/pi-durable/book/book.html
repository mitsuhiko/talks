Before you start

How to read this book

This book exists to make a ten-minute talk possible. Ten minutes is too short to teach Pi Durable. It is long enough to leave people with one picture in their heads, and to give that picture you have to understand the whole thing first. The book tries to get you there.

It deliberately avoids code. Where code appears, it shows a shape, never an API to memorize. The goal is that you can explain Pi Durable on a whiteboard: what is stored, who does the work, what happens when the power goes out.

  • Part I explains why Pi Durable exists: the assumptions a terminal coding agent can make, why they stop holding once agents leave the terminal, and how the design arrived where it is.
  • Part II is the architecture, in the order you would explain it: the one rule everything follows, what lives in storage, tasks, a turn taken apart, ownership, and then the features that fall out of those.
  • Part III walks through three scenarios in slow motion. These are the raw material for a demo that explains instead of just showing.
  • Part IV turns all of it into options for the talk: demo formats, a ten-minute structure, and a list of facts to double-check before going on stage.

If you only have half an hour: read chapters 2, 5, 7, 9 and 17. Those are the spine of the talk.

Sources

The normative specification in packages/durable/docs/spec.md (about 5,300 lines), the package README, the examples in test/examples, the git history of packages/agent and packages/durable, and the launch post on earendil.com. Where this book interprets rather than reports, it says so.

Part I

Why

A coding agent in a terminal can lean on a human for recovery. An agent in Slack, in an inbox, or in a Durable Object cannot. Pi Durable is what you build when no human is watching the process.

Chapter 1

The agent that lives in a terminal

Pi, the coding agent, runs on your machine (or a remote one), inside a terminal, driven by one person. It is minimal by design: a short system prompt, four tools, and an extension system that lets people mold it into what they need. More than five thousand extensions exist because of that malleability.

Pi stores a session as a transcript: a tree of entries, one JSON object per line, on disk. The process runs the agent loop: send the transcript to the model, run the tool calls it asks for, append the results, repeat until the model answers. The interesting state while this happens lives in memory: the half-streamed answer, the output of a running bash, the message you typed while the agent was busy, the retry it is about to attempt.

When the process dies, all of that is gone, and that is fine. You look at the transcript, see where it stopped, and type “continue”. The human is the recovery mechanism. Pi 1.0 is built around this, excels at it, and is not going to change.

The assumptions a terminal agent gets to make

It is worth spelling out what this design quietly relies on, because each of these is something Pi Durable had to give up:

AssumptionWhy it holds in a terminal
One process, one session, one humanYou started it, you are watching it, nobody else types into it.
The conversation lives as long as the processSessions last minutes or hours; you close the laptop, you restart.
In-flight state can be volatileIf a tool call is lost, you will notice and redo it.
The transcript is the only stateThere is no application around the agent that needs its own durable state.
The UI is in the same processEvents flow from the loop to the screen in memory.
The code is fixed while it runsTo change an extension you reload; a run in progress is your problem.

None of these are flaws. They are what makes a terminal agent small. But every one of them breaks the moment the agent is not a program you are personally watching.

Chapter 2

Agents leave the terminal

Earendil wants this technology in front of everyone, in whatever form fits them: Lefos answers by email, a bot answers mentions in Slack, a triage bot labels GitHub issues, an agent runs inside a Cloudflare Durable Object behind a web page. None of these has a human watching the process.

The launch post names five requirements. Each one breaks one of the assumptions from the last chapter.

RequirementBreaks the assumption that…What it forces
Runs anywherethere is one machine with a file system and NodeStorage and execution behind small interfaces; no Node APIs in the core.
Reachable from different surfacesthe UI lives in the processUIs attach to committed state, from anywhere, at any time.
Infinitely long conversationsa conversation fits in a process lifetime and in a context windowBounded memory, compaction while working, nothing ever deleted.
Survives catastrophic failuresin-flight state can be volatileEvery step checkpointed; a new process continues the old one’s work.
Multiple humans steer the same agentsone person types into itDurable queues, steering, exactly-once submission.

There is a sixth requirement that is easy to miss: malleability. Pi’s soul is that you change it. An agent that runs for weeks still needs its code changed, and you cannot stop the world to do it.

Who recovers when nobody is watching?

This is the core of the “why”. In the terminal, a crash is an inconvenience. In a Slack bot, a crash in the middle of a tool call means a question that is never answered, a deploy that may or may not have happened, and a user who asked twice because the bot looked dead. When the container is redeployed, the laptop sleeps, or the machine runs out of memory, someone has to know what was in progress and what to do about it.

If the human is no longer the recovery mechanism, the harness has to be. That single sentence is the reason Pi Durable exists.

Why not change Pi the coding agent?

Because Pi works and people depend on it. Pi Durable is a separate, experimental package. It shares code with the coding agent (model access through pi-ai) and its principles (minimalism and malleability), but it is a framework for building any agentic application, coding agents included. It is also a place to try designs without disrupting Pi: lessons that prove themselves are meant to flow back.

For the talk

“A coding agent can rely on you to notice that it died. A Slack bot can’t. Pi Durable is what you build when nobody is watching the process.”

Chapter 3

The road to Pi Durable

Pi Durable did not start as a database of tasks. It started as a much more modest idea: keep the session file, and add recovery notes to it. The git history shows the design moving, over about ten weeks, from one to the other.

A timeline from the repository

When (2026)What happened
28 JulyA first “Durable AgentHarness” design document lands in packages/agent: about 2,100 lines. It keeps Pi’s session log and adds private harness entries to it.
AugustHarness v2 and v3 implementations, designs for plugins and reload, sessions/branches/lanes, a “durable drive” runtime. Many design documents, many revisions.
Early SeptemberA series of prototypes named Pico: a pico2 spike, a hardened pico3 kernel, then Pico5, built on Chord’s transactional replicated state.
18 SeptemberPico moves into its own package: packages/durable. Over the next two weeks: SQLite and JSONL storage, transactional sessions, documents, forks, the task runtime, the Harness, structured concurrency.
1 OctoberShipped as experimental alongside Pi 1.0, together with a small coding agent and a vacation planner built on it.
SinceDurable code mode, nested tool calls, tool search, structured output, a stricter error model. About 150 commits touch the package.

Version one: a transcript with recovery notes

The July design is a natural first idea. Pi already has an append-only session log. So: write extra, private records into the same log as you go: “operation started”, “tool started”, “message queued”. They are never shown to the model and never part of the tree. After a crash, a recovery procedure reads the end of the log, works out how far the run got, and continues. Its central invariant reads:

Session entries define what the conversation is. Harness entries define what the harness did, in what order.

It also had to say what it could not do: at most one operation per session at a time, hooks never re-run after a crash, provider streams never persisted.

Where it ended up: a database of records

The specification that ships today opens with a different core rule:

A Session atomically commits immutable entries, full task records, and Chord-tracked documents. Only committed state is observable.

Read the two side by side and you can see the shift. (This is an interpretation, but the documents support it.)

July: log plus recovery notesOctober: Pi Durable
Source of truthThe transcript, with orchestration facts beside itConversations, entries, tasks, submissions and documents, all committed together
RecoveryA procedure that reads the log and reconstructsNot special: running tasks become pending, the scheduler continues
ConcurrencyOne operation per sessionAny number of conversations and tasks, in one ownership tree
In-flight stateVolatile; partial streams never persistedCommitted: partials and tool output are durable documents
UI modelSnapshot plus live eventsSnapshot plus exact operations of each commit
Application stateNot addressedTyped documents, committed with the transcript

The lesson is the most interesting thing to say about the history in a talk: recovery stopped being a feature and became a consequence. If every unit of work is a durable state machine and nothing is visible until it is stored, there is nothing to reconstruct. A new process simply has the same state the old one had.

For the talk

“Our first design was a transcript with recovery notes in the margin. The design we shipped is a small database where the transcript is just one table, and every piece of work is a row that knows where it was.”

Chapter 4

A vocabulary for harnesses

Everybody has their own definition of “harness”. Earendil’s earlier post compared it to a climbing harness: it holds you safely, connects you to ropes and tools, and you adapt it to the climb. Pi Durable needs a sharper definition, because it is a harness for building harnesses.

A harness is storage plus the machinery needed to run one or more conversations with large language models in parallel. It provides the tools those models call, and the execution environments the tools run in.

Six words carry the rest of this book:

WordMeaning
ConversationAn interaction between you and an agent, recorded as a transcript of immutable entries.
AgentThe model together with its settings (thinking level, instructions) and the tools it can call. Stored per conversation.
ToolSomething the model can call. Each call is durable work of its own.
Execution environmentWhere tools touch files and processes: your laptop, a remote VM, a container, an in-memory sandbox.
TaskEverything the harness runs, from calling the model to executing a tool, is a task: a durable state machine.
ExtensionA named bundle of prompt sections, tools, hooks and tasks. Conversations select extensions by name.

Like everything in Pi, Pi Durable is meant to be understood by your agent. At launch the source, without tests, was about 15,000 lines (about 150,000 tokens for GPT, 250,000 for Claude) and it has grown since. An agent building on it rarely needs all of it; the storage backends alone are 3,000 lines it can usually skip.

Part II

How it works

One rule, five kinds of records, and one kind of worker. Almost every feature of Pi Durable falls out of these.

Chapter 5

The one rule: commit before you show

If you remember one thing about Pi Durable, remember this: nothing is visible until it is stored. Not a streamed token, not a line of tool output, not a queued message. Everything else is built on that rule.

The mutation line

A harness opens over one storage. Inside it, a Session owns a single mutation line: a serialized queue through which every change passes. A change is a commit: a function that, in one transaction, may append transcript entries, change documents, create tasks, and record submissions. Either all of it is stored, or none of it is.

Two consequences follow immediately:

  • Effects never run inside a transaction. A commit cannot wait on a model, a process or a human. This keeps commits short and makes the boundaries between “decided” and “done” explicit.
  • There is no volatile path to the screen. A streaming answer is committed as a partial at most every 100 milliseconds. A tool’s running output is committed the same way. A UI sees them because they are in storage, not because the process told it.

Why this one rule buys so much

PropertyWhy it follows
A crash loses almost nothingWhatever anyone saw was stored. At most the last throttle window of streaming (100 ms by default) is gone.
Recovery is just reopeningThe new process reads the same state the old one was showing. There is no second copy to reconcile.
Any number of viewersA UI is a reader of committed state. Ten UIs, or one that joins late, all read the same thing.
Consistency between partsA tool’s result entry and the todo list it updated are in the same commit. They can never disagree.
Memory is a cacheThe process keeps a working set in memory. Anything not in use can be dropped and reloaded.
An analogy

The screen is a window onto the database, not onto the process. When the process dies, the window does not go dark: it just stops changing until a new process takes over the same database.

The price

Every visible change costs a commit. Partials are throttled so this stays cheap on local SQLite; a host with remote storage can commit less often (say every 500 ms). And one process owns a storage at a time: there is no cross-process locking. Other clients attach to that process.

Chapter 6

What lives in storage

Storage holds four tables of records and one kind of mutable state. That is the entire durable model. If you can draw this page, you understand what survives a crash.

The four tables

Conversations are transcript scopes. A conversation has two optional edges: a parent (it was forked from that conversation at a given entry) and an owner (a task created it, as a subagent). These two edges are deliberately separate: one is about history, the other about responsibility.

Entries are the transcript. They are immutable, their IDs are ordered across the whole session and never reused. Built-in kinds are user messages, model answers, tool results, system prompt changes, resets and compaction summaries. Applications add their own kinds, for example a chat mention that shows who asked.

Tasks are units of work with a stored checkpoint. They are the subject of the next chapter.

Submissions are what someone handed to a conversation: user input (which asks the model something) or a write (an entry to append without asking anything). A submission moves from queued to placed to done, or ends unanswered with a reason. An optional requestId makes it exactly-once: submit the same request ID again, after a crash or a network retry, and you get the original submission back.

Documents: the part that changes

Entries never change, but some things obviously do: the model selected for a conversation, the output of the tool that is running right now, the queue of messages typed while the agent was busy, the money spent. These live in documents: typed JSON values stored next to the transcript and changed in the same commits. Under the hood, a document change is recorded as a small list of JSON operations (via Chord, Earendil’s replicated-state library), with an occasional full copy so that replay stays short.

The built-in documents are worth knowing by name, because they are what makes “what is happening right now” durable:

DocumentHolds
pi.agentWhat this conversation runs with: model, thinking level, selected extensions and tools (as names), instructions, working directory.
pi.liveThe run in progress: the streaming partial answer, retry backoff, every running tool call with its output so far, nested calls, compactions in flight.
pi.inboxSubmissions waiting for a turn boundary: steers, follow-ups, writes.
pi.usageTokens and cost, per model and per tool, including failed and aborted attempts.
pi.providerA stable ID given to the model provider, so prompt caches keep working across restarts.

Documents also have a lifetime: session documents live forever, conversation documents belong to a conversation, and task documents disappear when their task finishes. And conversation documents declare what a fork sees: the value at the fork point, the current value, or a fresh one. That is a product decision, not an optimization (chapter 14).

The storage itself

The storage interface is small. Pi Durable ships four backends and a conformance suite plus benchmarks for writing your own (a key-value store or Postgres would do):

BackendNotes
MemoryNothing persisted. Tests and throwaway agents.
SQLiteOne file. Keeps only the working set in memory: active transcripts, live tasks, pending submissions. The choice for long-running agents.
JSONLAppend-only files in a directory. Keeps the whole history in memory.
Durable ObjectThe SQLite storage of one Cloudflare Durable Object.

The SQLite and JSONL cores use no Node APIs, so with a small adapter they run on Bun or inside a Durable Object. Because active transcripts are bounded by the model’s context window (compaction sees to that), even a conversation with tens of thousands of messages keeps a small memory footprint on SQLite.

Chapter 7

Tasks: work as durable state machines

Everything the harness runs is a task: each request to the model, each tool call, each compaction. Extensions bring their own. A task is a small state machine whose current state is a row in storage, so a process that has never seen it before can pick it up.

The shape of a task

A task definition has a name and a version, a set of named phases, and an abort handler. A task record stores its input and a checkpoint: which phase is next, plus whatever that phase needs. A phase runs some code and ends by committing one of three things:

  • a new checkpoint (“next, do phase B with this data”),
  • a wait (“resume at phase C once these other tasks are done”), or
  • an outcome (completed, failed, aborted).

Two scheduler rules make this robust:

  • A phase must make durable progress. If a phase returns without having changed its checkpoint or committed an outcome, the task is faulted. Progress that is not written down does not count.
  • On reopen, running becomes pending. Waiting tasks stay waiting. Nothing else happens at open; the scheduler later reserves pending tasks like any others and runs the phase in their checkpoint. There is no separate recovery code path per feature.

The effect sandwich

This is the most important idea in the task model, and the most honest one. Durability cannot make an external effect happen exactly once: if the process dies while a card is being charged, nobody knows whether the bank saw the request. What durability can do is make that uncertainty explicit and local:

A task that restarts in the middle knows precisely which effect is in doubt, and decides: retry safely with an idempotency key, poll an external handle (“is job 42 done?”), or report the interruption to whoever can decide. Tool calls use exactly this (chapter 8): a tool marked replay safe is simply run again; any other tool is reported to the model as interrupted, never repeated.

Memos: decisions you only make once

Sometimes a step has to decide something that must not be decided twice: an approval asked in Slack, a random choice, a generated name. A memo is a small value stored with the task where the first write wins. A hook that asks a human for approval stores the answer in a memo; after a restart it finds the stored answer instead of asking again.

Time, versions, and missing code

  • Timers survive restarts. A task sleeps until a wall-clock time stored in its checkpoint. A retry backoff is “retry at 14:02:10”, not “in five seconds”. A reminder that fires tomorrow is a task asleep until tomorrow.
  • Tasks are versioned. A new definition can migrate old checkpoints when it reserves them.
  • Missing code blocks, never destroys. If a task’s extension is not installed (yet), the task stays pending and is reconsidered when the registry changes. The harness never marks work failed just because the code to run it is temporarily missing.
For the talk

“Durability can’t make a side effect happen exactly once. What it can do is tell you, after a crash, exactly which effect is in doubt.”

Chapter 8

One turn, taken apart

With the vocabulary in place, here is what actually happens when you ask an agent something. One answered question is a small tree of tasks, and every arrow below is a commit.

Step by step

  1. Admission. submit() durably records the input. If the conversation is idle it is placed at once as a pi.user entry, and a generation task is created. pi.live.run now says the conversation is busy and which task holds the run.
  2. Prepare. The generation resolves the conversation’s agent, renders the system prompt sections, and compares them with what the transcript says the model last saw. If anything changed, it appends a pi.system entry with only the difference. It checks whether the context is getting too long (chapter 12), then commits its next checkpoint: request, pinned to a model, a thinking level, and the last entry to include.
  3. Request. The model streams. Every 100 ms or so, the partial answer is committed to pi.live. That is how every attached UI sees tokens appear.
  4. Tool round. The response asks for three tools. One commit appends the answer, creates three pi.tool tasks owned by the generation, and puts the generation into waiting on them.
  5. Each tool. A tool task validates the arguments and runs the beforeTool hooks (which may rewrite or block the call). Then it commits its intent: the final arguments and whether the tool is replay safe. Then it executes, streaming output into pi.live. Then it commits the pi.tool-result entry and finishes.
  6. Boundary. When all three are terminal, the generation wakes up in its tools phase. This is a turn boundary: queued steering messages are placed here. It creates the next generation and hands it the run.
  7. Answer. The second generation’s answer has no tool calls. One commit appends it, marks the submission done, and clears the run. The conversation is idle.

Where can it die, and what happens then?

The process dies…On reopen
after submit() returnedThe input is stored. It is placed and answered as usual. A client that resubmits with the same requestId gets the same submission back, not a second question.
while the model streamsThe committed partial is kept in the transcript as an aborted answer (visible, never sent to the model again). The same request is sent again, with the same pinned model and messages.
during a retry backoffThe generation sleeps until the stored deadline, then retries.
while a tool runsReplay-safe tool: it runs again with the stored arguments. Otherwise: an interrupted error result, with the output stored so far, goes to the model, which decides what to do.
while the generation waitsIt is still waiting; it resumes when its tools are done. Nothing to do.
in a subagentThe subagent is a conversation like any other; its own tasks resume (chapter 10).
Why one task per request

Splitting a run into a fresh generation task per model request, and a task per tool call, is what makes all of the above uniform. Each piece has its own checkpoint, so recovery is always local: continue this request, rerun this tool. The run itself is just a pointer in pi.live, handed from one generation to the next.

Chapter 9

One ownership tree

Durability answers “what happens after a crash”. Ownership answers the other hard question of long-running agents: “what happens when someone presses Esc?” In Pi Durable, all tasks and conversations form one tree, and that tree decides what an abort reaches and when something is finished.

The rules

  • Everything names its owner. A task is owned by its conversation or by another task. A conversation is ownerless or owned by a task. A subagent is simply a conversation owned by the tool call that started it.
  • Abort flows down. Aborting something aborts what it owns.
  • Cleanup runs bottom-up. A task’s abort handler starts only after everything it owns has finished. So each task cleans up its own effects, and a parent’s handler sees the final outcome of its children.
  • Owned work does not outlive its owner’s finish. A task that decides its outcome while its children still run is held as completing until they drain. When a tool call returns, its subagent is really done.
  • Background is a boundary. A background task belongs to the conversation but not to its current work. The conversation goes idle while it runs, and Esc leaves it alone. Aborting the task itself, or the conversation with { background: true }, still stops it.

Waiting together

A task can create children and then wait for them without running any code. With allSettled it resumes when all are done. With failFast, the first failure aborts the others. Chapter 19 uses this for a checkout that charges several cards at once and refunds them all if one is declined.

Aborted versus orphaned

There is a fine but important distinction in the outcomes. Aborted means the task’s own abort handler ran and cleaned up. Orphaned means its code was not available (its extension was uninstalled, say) and someone aborted it anyway: no cleanup ran, and effects it started may remain. The harness never pretends cleanup happened.

For the talk

“Durability is the easy half. The hard half is Esc. When you press it, what stops? In Pi Durable, the answer is a tree, and cleanup runs from the leaves up.”

Chapter 10

Many conversations: forks and subagents

One harness runs as many conversations as you need, concurrently, all with the same guarantees. New conversations start fresh, fork an existing one, or are created by a tool as a subagent.

Forks share history without copying it

A fork names a parent conversation and an entry in it. It sees the parent’s transcript up to that entry, then continues on its own. Nothing is copied; reading a fork’s history walks its own entries, then the parent’s up to the cut.

Each conversation has its own agent

The pi.agent document stores, per conversation, what it runs with: model, thinking level, the selected extensions and which of their tools are active, extra instructions, and a working directory. A reviewer next to the main agent can use a cheaper model, read-only tools, and its own checkout. The Slack thread may search issues but not deploy.

Because the agent is a rewindable document, a fork starts with the agent its parent had at the fork point, not now. A subagent starts as a copy of its owner’s agent at creation, and is then adjusted.

A subagent is a few lines, not a feature

Pi Durable has no built-in subagents, and that is the point: the primitives make them trivial. A subagent tool, described in prose:

  1. In one commit: look for a conversation already owned by this tool call; if there is none, create one owned by it, and configure it with a smaller model and its own instructions.
  2. Tell the UI which conversation it is, so the UI can show it under the call.
  3. Submit the task to the child with a request ID derived from the tool call (triage:<task id>), and wait for the answer.
  4. Return the answer as the tool result.

Now look at what that buys, without writing anything else:

  • Crash: the tool is replay safe. A rerun finds the same child (step 1 looks it up first) and the same submission (same request ID), and keeps waiting for the same answer. The child’s own tasks resumed on their own.
  • Esc: the child is owned by the call, so aborting the parent aborts the child, bottom-up.
  • Idle: the parent is not idle until the child is.
  • Cost: the child counts its own usage.
  • UI: the child is a conversation like any other. You can watch it, and you can steer it.

The background variant is a subagent owned by a background task: the tool returns immediately, the main agent keeps chatting, and a small task delivers the child’s report back to the main conversation as a follow-up message when it arrives. The vacation planner (chapter 18) is built exactly like this.

Chapter 11

The inbox: many people, one agent

In the terminal you rarely type while the agent works, and if you do, it is you. In a Slack channel, anyone can mention the agent at any time, and the person who asked the first question may want to correct it mid-flight.

A conversation is busy while a run is working on an input. Anything submitted to a busy conversation goes into its durable inbox (pi.inbox) and is placed at a turn boundary, where it is safe to add to the transcript (never between a tool call and its result). Each submission says how it wants to be treated:

ModeBehavior
steerPlaced after the current tool round and joins the running work. “Check the staging logs first.”
follow-upThe default. Placed when the run answers, and starts the next run. “Also run the tests.”
rejectOnly if idle; otherwise the submit fails.
writeAppends an entry without asking the model anything. A display-only write (a chat message, “user opened a file”) is appended at once, even mid-run.

Because the inbox is a document, every attached UI shows the queue, a queued message can be withdrawn, and a crash loses nothing that was queued. Because submissions take a requestId, a Slack webhook that is delivered twice asks the agent once.

An input can also be placed as an application entry: the model still sees “ann: can you check the build?” as a user message, but the transcript records a chat.mention with the author, which is what a UI wants to render.

This is the multiplayer mechanism

“Multiple humans steer the same agents” is not a separate feature. It is the inbox, plus the fact that every client reads the same committed state (chapter 14).

Chapter 12

Context without end

A conversation that lasts weeks will not fit in any context window. Pi Durable keeps everything in storage forever and changes only what the model sees, without stopping the agent to do it.

Heads: where the model’s view begins

The transcript only ever grows. Some entries carry a head: a marker that says “from here on, the model’s context starts at entry N”. The active transcript is everything from the newest head to the tail. Older entries are still in storage and still searchable, just no longer sent.

Compaction is a task that runs while the agent works

In the terminal agent, compaction is something the agent stops to do. In Pi Durable, compaction is a task like any other, and it runs concurrently:

  • When the context gets within a configurable distance of the limit, a background compaction starts summarizing older messages. The agent keeps working.
  • The summary is placed at the next turn boundary, like a queued message.
  • The conversation only waits for a summary when the next request would not fit otherwise.
  • If the provider still rejects a request as too long, the harness compacts and retries once.
  • You can compact manually at any time, with your own instructions, also while the agent works.

Reset and handoff

reset() goes further: it starts a new context, optionally from a handoff note. A tool can request the same by returning a handoff. Because nothing is deleted, a second tool can still search everything before the handoff. That is all it takes to build an agent that hands off to itself and looks things up later.

The system prompt is part of the transcript

One more subtle piece. The system prompt is rebuilt from the selected extensions’ sections before every request, so a changed section (an updated AGENTS.md, a new todo list) is picked up by the next request. But what the model saw is recorded in the transcript as positional pi.system entries holding only the differences: “section cwd changed”, “tool read removed”. Two things follow:

  • A restart or a fork sees exactly what the model saw, at the position where it changed.
  • On models that support it, only the change is sent, so the provider’s prompt cache stays valid.
Chapter 13

Extensions: names, not code

Pi is malleable, so Pi Durable has to be. The trick that makes it possible for long-running agents is small: conversations store extension and tool names, never code.

Extensions and the registry

An extension is a named bundle of system prompt sections, tools, hooks, tool wrappers, and task definitions. The application installs extensions in a registry that the process owns. By default every conversation selects every installed extension; each can narrow that.

  • A later extension’s tool with the same name replaces an earlier one (a bash that runs inside a virtualenv).
  • A wrap decorates whichever tool won (time every bash call, whichever bash it is).
  • Hooks step into the built-in tasks: rewrite a request before it goes to the model, block or rewrite a tool call, replace a result, keep a run going, write a compaction summary yourself. Several extensions can hook the same point; their hooks run as a chain in selection order.

Hot reload, for free

The registry can change while conversations run. Installing an extension under a name that is already installed replaces it in one step:

  • A tool call that is already running finishes on the code it started with. The next call uses the new code.
  • A task picks up new code at its next phase boundary.
  • After a restart, conversations pick up whatever the new process installs, because they only stored names.
  • A stored name that is not installed right now is skipped, not an error. When it is installed again, it takes effect again.

This is the same mechanism that makes recovery work: the durable state never contains anything a different version of the code cannot read.

Hooks have to be durable too

A hook can run again after a crash. So a hook that makes a decision stores it in a memo. The canonical example: a beforeTool hook that asks for approval in Slack before any deploy. The answer is a memo on the tool task. After a restart, the hook finds the stored answer instead of asking again.

Tools calling tools, and durable code mode

A tool can call another tool. The nested call is its own task, owned by the caller, with its own hooks and replay policy. This is the basis for code mode: the model writes a small JavaScript program that calls the conversation’s tools, run in a QuickJS sandbox. The clever part is how a script survives a restart:

  • The sandbox is deterministic: a virtual clock, seeded randomness, UTC.
  • Every result a script receives is written to a journal before the script gets it.
  • After a restart, the script runs again from the top; it is handed the journaled results in the same order, so it makes the same calls with the same arguments, which reattach to the nested calls already made. Then it continues where it was.
  • If the script takes a different path than before, or the sandbox changed, the call ends with an error instead of guessing.

This is the effect sandwich again, applied to a program instead of a single call.

Chapter 14

Documents, views and multiplayer

An agent is rarely the whole application. There is a todo list, a plan, a ticket, a shopping cart, the sandbox the conversation runs in. In Pi Durable this state is as durable as the conversation, and every client sees it the same way.

Your state, in the same commit

Application state lives in documents: typed JSON stored next to the transcript and changed in the same atomic commits. A todo tool that adds an item appends its tool result and changes the todo document in one commit, so the state never disagrees with the transcript that produced it. A prompt section can render the document so the model sees the list before every request; a UI subscribes to the committed value.

Each document says what a fork starts with, and this is a product decision:

Fork modeA fork starts with…Example
asOfthe parent’s value at the fork pointtodos: the thread sees the list as it was then
currentthe parent’s value nowa container assignment
initiala fresh valuea scratchpad, the provider session ID

Views: snapshot, then exact changes

Everything a UI needs is committed state. A client that attaches to a conversation gets the current view first: the active transcript, the answer being streamed, running tools and their output, queued messages, the agent, usage. After that it gets only what changes, as the exact JSON operations of each commit: small enough to send over a WebSocket.

  • Late join: a client that joins mid-run, or reconnects, starts from the current view. Nothing is replayed.
  • Slow clients: a watch buffers up to 100 commits. Past that, the backlog is replaced by one frame with the whole current view.
  • Familiar events: if you prefer the coding agent’s events (message start, message update, tool execution start…), watchEvents() derives them from the commits, at the cost of more bytes.
  • Task graph: every live task of the session as one view, for a task panel or for debugging.

Combined with the inbox, this is multiplayer: any number of people and clients watch the same conversation, join late, and steer it.

Why this falls out of the one rule

Because nothing is shown before it is stored, a “live view” and a “view after a restart” are the same thing. There is no event stream that has to be kept consistent with the database: the stream is the database’s commits.

Chapter 15

Running anywhere

“Anywhere” currently means anywhere there is a JavaScript runtime. Two small interfaces make that possible: storage, and the execution environment.

The execution environment

Tools that need files or a shell get them from an execution environment, never directly from the machine the harness runs on. Pi Durable ships a Node environment for local files; the interface is small enough to implement for a remote VM or a container. An env function builds the environment for every tool call, from the conversation’s working directory and its documents. So:

  • the harness can run on one machine while its tools run on another;
  • each conversation can run in a different place: a directory per conversation, or a container per conversation recorded in an application document;
  • a tool rerun after a crash gets the conversation’s environment at that time.

Example: an agent in a Durable Object

There is an example project (pi-durable-cloudflare) that hosts a harness inside a Cloudflare Durable Object. It is a good illustration of how little glue “anywhere” needs:

  • Each named agent session is one Durable Object; the harness state is its SQLite.
  • The browser talks to it over one WebSocket and renders the event stream.
  • A schedule tool creates a durable task that delivers an instruction back to the same conversation when it is due. The earliest deadline becomes the Durable Object’s alarm.
  • When Cloudflare evicts and later reconstructs the object, the alarm wakes it, the harness reopens, and every task continues from its checkpoint.
  • A recall tool is a foreground subagent that searches other conversations and answers briefly, so raw matches never enter the parent’s context.

Eviction, hibernation, redeploys: to Pi Durable these are all the same event as a crash, and handled the same way.

Chapter 16

What can go wrong, and what is not promised

A durable system is defined as much by what it refuses to promise as by what it does. This chapter is useful for the Q&A.

Three rules decide what an error does

  1. A storage error ends the harness. If storage fails, nothing can be recorded, so nothing may continue. The harness fails, closes itself, and must be reopened. Commits are atomic, so the store is consistent; resubmitting with the same request ID finds what was already admitted. Storage retries its own transient failures.
  2. An invalid request fails only that call. A bad cursor, an unknown conversation.
  3. Your code fails only its own unit. A throwing task phase faults that task. A throwing tool gives the model an error result. A throwing hook is reported and skipped, except beforeTool, where a throw blocks the call (failing closed).

What Pi Durable does not do

Not promisedInstead
Exactly-once external effectsThe effect sandwich makes the doubt explicit; idempotency keys, polling, or “interrupted” resolve it.
Several processes writing one storageOne owner at a time, no cross-process lock. Other clients attach to the owner.
Offline multi-writer merge (CRDTs)One line of commits; documents are changed by one writer.
Killing misbehaving code in-processCode that ignores its abort signal delays close until it returns.
Power-loss durability on JSONL by defaultOpt into fsync, or use SQLite (WAL; the newest commit may be lost on power failure).
A stable APIIt is experimental. The API changes between releases.

Footguns worth knowing

  • Long transactions. Never await a model, a process or a human inside a commit. It holds the line for everyone.
  • Owned work holds its owner. A subagent you keep talking to keeps the tool call that owns it in completing. Work that should not hold its owner is created as background.
  • Unstable prompt text. A section that embeds the current time changes on every request, appends a system delta every time, and defeats prompt caching.
  • Guards are selected, not global. A conversation whose extension selection omits the permissions extension runs without it.

  • There was no recovery code. Reopen moved one row from running to pending. Everything else is the ordinary machinery: a task in a phase, a boundary, a new generation.
  • The harness did not guess. It did not rerun npm test on its own, and it did not pretend the test run finished. It told the model exactly what is known.
  • The second person was not lost. The steer was durable before the crash and placed at the first boundary after it.
  • The search was not repeated. It had finished; its result was in the transcript. Had it been interrupted too, it would simply have run again, because it is marked safe.
  • Slack sees one answer. The request ID made the retried webhook a no-op.
For the talk

This chapter is the best candidate for the demo. Its shape is: show the work as rows appearing, pull the plug, show that the rows are still there, start a new process, and show that exactly one row changes before work continues.

Chapter 19

Not just for models: a split payment

The task machinery is not specific to language models. The launch post makes that point with a checkout that splits the bill across several cards. It is the clearest illustration of ownership, waiting and bottom-up cleanup.

Two task types

  • Payment has one phase, charge: charge one card with the idempotency key payment-<task id>, then commit the receipt or the decline as its outcome. Its abort handler refunds by the same key.
  • Checkout has two phases. pay creates one Payment per card, owned by the checkout, and commits “wait for all of them, fail fast”. decide reads their outcomes and commits “order placed” or “a payment failed”.

An agent starts a checkout with a tool. The checkout is owned by that tool call.

Four things that can happen

ScenarioWhat the tree does
All four cards go throughEach payment completes. The checkout, which ran no code while it waited, resumes in decide: placed.
One card is declinedThat payment fails. failFast marks the others that are still in flight for abort (here: all three). Each runs its own abort handler: a refund. When all four are terminal, the checkout resumes and reads [aborted, failed, aborted, aborted].
The user presses EscAbort flows down from the conversation, through the generation and the tool call, to the checkout, to the payments. Cleanup runs from the bottom: payments refund first, then the checkout’s abort handler sees their final outcomes.
The process dies mid-paymentThe payments still in charge become pending and charge again, with the same key, so the bank charges once. The checkout is still waiting and resumes when they are done.

Notice that “refund on cancel” was written once, in the payment’s abort handler, at the level that did the effect. Nobody above it needs to know how to undo a charge.

A subtlety worth knowing for Q&A

failFast aborts only the payments that are still live. A payment that already completed before another was declined is not aborted, so its abort handler does not refund it. In the example in test/examples/24-child-tasks.ts the expired card is declined at once, before any other charge completes, so all three others are refunded. A production checkout would refund completed payments in its decide phase. The machinery gives you the outcomes; the compensation policy is still yours.

Chapter 20

How to demo something you should not demo live

The thing Pi Durable is good at is invisible when it works. A durable agent that answers a question looks exactly like a non-durable one. The interesting moment is a failure, and failures on stage are either fake or risky. So the demo has to make the invisible visible.

What the demo must show

  1. Work in progress is stored, not held in memory.
  2. The process dies, and the state does not.
  3. A new process continues, and changes almost nothing to do so.
  4. Effects in doubt are handled honestly: rerun if safe, otherwise reported.

A terminal demo shows 2 and 3 but not 1 or 4: you see the agent stop and start again, and you have to take the rest on faith. That is the argument for explaining the architecture rather than just running it.
