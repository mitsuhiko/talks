Chapter 10

Many conversations: forks and subagents

One harness runs as many conversations as you need, concurrently, all with the same guarantees. New conversations start fresh, fork an existing one, or are created by a tool as a subagent.

Forks share history without copying it

A fork names a parent conversation and an entry in it. It sees the parent’s transcript up to that entry, then continues on its own. Nothing is copied; reading a fork’s history walks its own entries, then the parent’s up to the cut.

Each conversation has its own agent

The pi.agent document stores, per conversation, what it runs with: model, thinking level, the selected extensions and which of their tools are active, extra instructions, and a working directory. A reviewer next to the main agent can use a cheaper model, read-only tools, and its own checkout. The Slack thread may search issues but not deploy.

Because the agent is a rewindable document, a fork starts with the agent its parent had at the fork point, not now. A subagent starts as a copy of its owner’s agent at creation, and is then adjusted.

A subagent is a few lines, not a feature

Pi Durable has no built-in subagents, and that is the point: the primitives make them trivial. A subagent tool, described in prose:

  1. In one commit: look for a conversation already owned by this tool call; if there is none, create one owned by it, and configure it with a smaller model and its own instructions.
  2. Tell the UI which conversation it is, so the UI can show it under the call.
  3. Submit the task to the child with a request ID derived from the tool call (triage:<task id>), and wait for the answer.
  4. Return the answer as the tool result.

Now look at what that buys, without writing anything else:

  • Crash: the tool is replay safe. A rerun finds the same child (step 1 looks it up first) and the same submission (same request ID), and keeps waiting for the same answer. The child’s own tasks resumed on their own.
  • Esc: the child is owned by the call, so aborting the parent aborts the child, bottom-up.
  • Idle: the parent is not idle until the child is.
  • Cost: the child counts its own usage.
  • UI: the child is a conversation like any other. You can watch it, and you can steer it.

The background variant is a subagent owned by a background task: the tool returns immediately, the main agent keeps chatting, and a small task delivers the child’s report back to the main conversation as a follow-up message when it arrives. The vacation planner (chapter 18) is built exactly like this.

Chapter 11

The inbox: many people, one agent

In the terminal you rarely type while the agent works, and if you do, it is you. In a Slack channel, anyone can mention the agent at any time, and the person who asked the first question may want to correct it mid-flight.

A conversation is busy while a run is working on an input. Anything submitted to a busy conversation goes into its durable inbox (pi.inbox) and is placed at a turn boundary, where it is safe to add to the transcript (never between a tool call and its result). Each submission says how it wants to be treated:

ModeBehavior
steerPlaced after the current tool round and joins the running work. “Check the staging logs first.”
follow-upThe default. Placed when the run answers, and starts the next run. “Also run the tests.”
rejectOnly if idle; otherwise the submit fails.
writeAppends an entry without asking the model anything. A display-only write (a chat message, “user opened a file”) is appended at once, even mid-run.

Because the inbox is a document, every attached UI shows the queue, a queued message can be withdrawn, and a crash loses nothing that was queued. Because submissions take a requestId, a Slack webhook that is delivered twice asks the agent once.

An input can also be placed as an application entry: the model still sees “ann: can you check the build?” as a user message, but the transcript records a chat.mention with the author, which is what a UI wants to render.

This is the multiplayer mechanism

“Multiple humans steer the same agents” is not a separate feature. It is the inbox, plus the fact that every client reads the same committed state (chapter 14).

Chapter 12

Context without end

A conversation that lasts weeks will not fit in any context window. Pi Durable keeps everything in storage forever and changes only what the model sees, without stopping the agent to do it.

Heads: where the model’s view begins

The transcript only ever grows. Some entries carry a head: a marker that says “from here on, the model’s context starts at entry N”. The active transcript is everything from the newest head to the tail. Older entries are still in storage and still searchable, just no longer sent.

Compaction is a task that runs while the agent works

In the terminal agent, compaction is something the agent stops to do. In Pi Durable, compaction is a task like any other, and it runs concurrently:

  • When the context gets within a configurable distance of the limit, a background compaction starts summarizing older messages. The agent keeps working.
  • The summary is placed at the next turn boundary, like a queued message.
  • The conversation only waits for a summary when the next request would not fit otherwise.
  • If the provider still rejects a request as too long, the harness compacts and retries once.
  • You can compact manually at any time, with your own instructions, also while the agent works.

Reset and handoff

reset() goes further: it starts a new context, optionally from a handoff note. A tool can request the same by returning a handoff. Because nothing is deleted, a second tool can still search everything before the handoff. That is all it takes to build an agent that hands off to itself and looks things up later.

The system prompt is part of the transcript

One more subtle piece. The system prompt is rebuilt from the selected extensions’ sections before every request, so a changed section (an updated AGENTS.md, a new todo list) is picked up by the next request. But what the model saw is recorded in the transcript as positional pi.system entries holding only the differences: “section cwd changed”, “tool read removed”. Two things follow:

  • A restart or a fork sees exactly what the model saw, at the position where it changed.
  • On models that support it, only the change is sent, so the provider’s prompt cache stays valid.
Chapter 13

Extensions: names, not code

Pi is malleable, so Pi Durable has to be. The trick that makes it possible for long-running agents is small: conversations store extension and tool names, never code.

Extensions and the registry

An extension is a named bundle of system prompt sections, tools, hooks, tool wrappers, and task definitions. The application installs extensions in a registry that the process owns. By default every conversation selects every installed extension; each can narrow that.

  • A later extension’s tool with the same name replaces an earlier one (a bash that runs inside a virtualenv).
  • A wrap decorates whichever tool won (time every bash call, whichever bash it is).
  • Hooks step into the built-in tasks: rewrite a request before it goes to the model, block or rewrite a tool call, replace a result, keep a run going, write a compaction summary yourself. Several extensions can hook the same point; their hooks run as a chain in selection order.

Hot reload, for free

The registry can change while conversations run. Installing an extension under a name that is already installed replaces it in one step:

  • A tool call that is already running finishes on the code it started with. The next call uses the new code.
  • A task picks up new code at its next phase boundary.
  • After a restart, conversations pick up whatever the new process installs, because they only stored names.
  • A stored name that is not installed right now is skipped, not an error. When it is installed again, it takes effect again.

This is the same mechanism that makes recovery work: the durable state never contains anything a different version of the code cannot read.

Hooks have to be durable too

A hook can run again after a crash. So a hook that makes a decision stores it in a memo. The canonical example: a beforeTool hook that asks for approval in Slack before any deploy. The answer is a memo on the tool task. After a restart, the hook finds the stored answer instead of asking again.

Tools calling tools, and durable code mode

A tool can call another tool. The nested call is its own task, owned by the caller, with its own hooks and replay policy. This is the basis for code mode: the model writes a small JavaScript program that calls the conversation’s tools, run in a QuickJS sandbox. The clever part is how a script survives a restart:

  • The sandbox is deterministic: a virtual clock, seeded randomness, UTC.
  • Every result a script receives is written to a journal before the script gets it.
  • After a restart, the script runs again from the top; it is handed the journaled results in the same order, so it makes the same calls with the same arguments, which reattach to the nested calls already made. Then it continues where it was.
  • If the script takes a different path than before, or the sandbox changed, the call ends with an error instead of guessing.

This is the effect sandwich again, applied to a program instead of a single call.

Chapter 14

Documents, views and multiplayer

An agent is rarely the whole application. There is a todo list, a plan, a ticket, a shopping cart, the sandbox the conversation runs in. In Pi Durable this state is as durable as the conversation, and every client sees it the same way.

Your state, in the same commit

Application state lives in documents: typed JSON stored next to the transcript and changed in the same atomic commits. A todo tool that adds an item appends its tool result and changes the todo document in one commit, so the state never disagrees with the transcript that produced it. A prompt section can render the document so the model sees the list before every request; a UI subscribes to the committed value.

Each document says what a fork starts with, and this is a product decision:

Fork modeA fork starts with…Example
asOfthe parent’s value at the fork pointtodos: the thread sees the list as it was then
currentthe parent’s value nowa container assignment
initiala fresh valuea scratchpad, the provider session ID

Views: snapshot, then exact changes

Everything a UI needs is committed state. A client that attaches to a conversation gets the current view first: the active transcript, the answer being streamed, running tools and their output, queued messages, the agent, usage. After that it gets only what changes, as the exact JSON operations of each commit: small enough to send over a WebSocket.

  • Late join: a client that joins mid-run, or reconnects, starts from the current view. Nothing is replayed.
  • Slow clients: a watch buffers up to 100 commits. Past that, the backlog is replaced by one frame with the whole current view.
  • Familiar events: if you prefer the coding agent’s events (message start, message update, tool execution start…), watchEvents() derives them from the commits, at the cost of more bytes.
  • Task graph: every live task of the session as one view, for a task panel or for debugging.

Combined with the inbox, this is multiplayer: any number of people and clients watch the same conversation, join late, and steer it.

Why this falls out of the one rule

Because nothing is shown before it is stored, a “live view” and a “view after a restart” are the same thing. There is no event stream that has to be kept consistent with the database: the stream is the database’s commits.

Chapter 15

Running anywhere

“Anywhere” currently means anywhere there is a JavaScript runtime. Two small interfaces make that possible: storage, and the execution environment.

The execution environment

Tools that need files or a shell get them from an execution environment, never directly from the machine the harness runs on. Pi Durable ships a Node environment for local files; the interface is small enough to implement for a remote VM or a container. An env function builds the environment for every tool call, from the conversation’s working directory and its documents. So:

  • the harness can run on one machine while its tools run on another;
  • each conversation can run in a different place: a directory per conversation, or a container per conversation recorded in an application document;
  • a tool rerun after a crash gets the conversation’s environment at that time.

Example: an agent in a Durable Object

There is an example project (pi-durable-cloudflare) that hosts a harness inside a Cloudflare Durable Object. It is a good illustration of how little glue “anywhere” needs:

  • Each named agent session is one Durable Object; the harness state is its SQLite.
  • The browser talks to it over one WebSocket and renders the event stream.
  • A schedule tool creates a durable task that delivers an instruction back to the same conversation when it is due. The earliest deadline becomes the Durable Object’s alarm.
  • When Cloudflare evicts and later reconstructs the object, the alarm wakes it, the harness reopens, and every task continues from its checkpoint.
  • A recall tool is a foreground subagent that searches other conversations and answers briefly, so raw matches never enter the parent’s context.

Eviction, hibernation, redeploys: to Pi Durable these are all the same event as a crash, and handled the same way.

Chapter 16

What can go wrong, and what is not promised

A durable system is defined as much by what it refuses to promise as by what it does. This chapter is useful for the Q&A.

Three rules decide what an error does

  1. A storage error ends the harness. If storage fails, nothing can be recorded, so nothing may continue. The harness fails, closes itself, and must be reopened. Commits are atomic, so the store is consistent; resubmitting with the same request ID finds what was already admitted. Storage retries its own transient failures.
  2. An invalid request fails only that call. A bad cursor, an unknown conversation.
  3. Your code fails only its own unit. A throwing task phase faults that task. A throwing tool gives the model an error result. A throwing hook is reported and skipped, except beforeTool, where a throw blocks the call (failing closed).

What Pi Durable does not do

Not promisedInstead
Exactly-once external effectsThe effect sandwich makes the doubt explicit; idempotency keys, polling, or “interrupted” resolve it.
Several processes writing one storageOne owner at a time, no cross-process lock. Other clients attach to the owner.
Offline multi-writer merge (CRDTs)One line of commits; documents are changed by one writer.
Killing misbehaving code in-processCode that ignores its abort signal delays close until it returns.
Power-loss durability on JSONL by defaultOpt into fsync, or use SQLite (WAL; the newest commit may be lost on power failure).
A stable APIIt is experimental. The API changes between releases.

Footguns worth knowing

  • Long transactions. Never await a model, a process or a human inside a commit. It holds the line for everyone.
  • Owned work holds its owner. A subagent you keep talking to keeps the tool call that owns it in completing. Work that should not hold its owner is created as background.
  • Unstable prompt text. A section that embeds the current time changes on every request, appends a system delta every time, and defeats prompt caching.
  • Guards are selected, not global. A conversation whose extension selection omits the permissions extension runs without it.
