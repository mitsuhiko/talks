Part IV

Toward the talk

Ten minutes, one idea, one demo. These chapters are a starting point for a discussion, not a finished plan.

Chapter 20

How to demo something you should not demo live

The thing Pi Durable is good at is invisible when it works. A durable agent that answers a question looks exactly like a non-durable one. The interesting moment is a failure, and failures on stage are either fake or risky. So the demo has to make the invisible visible.

What the demo must show

  1. Work in progress is stored, not held in memory.
  2. The process dies, and the state does not.
  3. A new process continues, and changes almost nothing to do so.
  4. Effects in doubt are handled honestly: rerun if safe, otherwise reported.

A terminal demo shows 2 and 3 but not 1 or 4: you see the agent stop and start again, and you have to take the rest on faith. That is the argument for explaining the architecture rather than just running it.

Options

OptionWhat it isTrade-offs
A. The X-ray (recommended)A split slide. Left: a chat, as a user sees it. Right: the storage, as four small tables and the pi.live document. Each click is one commit; rows appear on the right while text appears on the left. Then the left side goes dark (“kill -9”), the right stays. A new process appears, one row changes from running to pending, and work continues.Zero risk; explains all four points; works at any speed. Needs building as an animated slide. Risk of feeling like a diagram, so it has to move.
A+. Recorded truthSame as A, but the data is real: run a real harness (faux model provider, SQLite) through the chapter 17 scenario, record every commit with the commit subscription or a watch, kill it, reopen, record again. The slide replays the recorded trace.Everything on screen is genuinely what the system wrote. A few hours of work; makes a great “this is not a mockup” line.
B. ScreencastA 30–45 second recording of the vacation planner: three searches, Ctrl+C with only trains left, --continue, only trains reruns, the report arrives. Sped up, with captions.Proof that it is real, with a real TUI and task panel. Must be recorded from v1.1.0 (the demo is gone on main). On its own it shows the effect, not the mechanism.
C. Live, deterministicRun an example like 13-recovery or 24-child-tasks live in a terminal. They use no network and print what happens.Real and safe, but terminal text is not a good visual for an audience, and it costs time.
D. Live killRun the planner or a Slack bot live, kill it, restart it.The most dramatic, and the most fragile: network, model latency, Wi-Fi. Not compatible with a ten-minute slot.
E. Two screensTwo browser tabs on the same conversation (the Cloudflare example): type in one, watch it in the other; reload one mid-answer; it comes back where it was.Shows multiplayer and late join beautifully. Also live and network dependent.

A suggestion

Make A (ideally A+) the spine of the talk, and do not call it a demo: call it following one message through the system. Then, optionally, close the section with ten seconds of B as the punchline (“and here is the real thing doing it”). That gives you the explanation and the proof without anything that can fail on stage.

Chapter 21

A ten-minute shape

One possible structure. The times add up to ten minutes; the slide counts are rough.

TimeSectionContent
0:00–0:45Hook“What happens when your agent dies?” In a terminal: you notice and type “continue”. You are the recovery mechanism.
0:45–2:30WhyAgents are leaving the terminal: Slack, email, GitHub, Durable Objects. Nobody watches the process. The five requirements (run anywhere, many surfaces, endless conversations, survive crashes, many humans), plus malleability. “If the human is not the recovery mechanism, the harness has to be.”
2:30–3:30How we got hereFirst design: the transcript plus recovery notes in the margin. What shipped: a small database where the transcript is one table and every piece of work is a row that knows where it was. Recovery stopped being a feature and became a consequence.
3:30–6:30Four ideas 1. Commit before you show. One line of commits; the screen is a window onto storage.
2. Everything is a task. Model requests, tool calls, compaction. Intent, effect, outcome. Durability can’t make an effect happen once; it can tell you which one is in doubt.
3. One ownership tree. Subagents are conversations owned by tool calls. Esc flows down, cleanup runs up. Background is a boundary.
4. Names, not code. Conversations store extension names; code comes from the registry. Hot reload and restarts are the same thing.
6:30–9:00Follow one messageThe X-ray (chapter 20): eight beats, the plug pulled at beat five. Optionally ten seconds of the vacation planner as proof.
9:00–10:00CloseExperimental, try it, point your agent at packages/durable. What we are building with it. The coding agent is not going away; lessons flow back.

Lines that might be worth keeping

  • “A coding agent can rely on you to notice that it died. A Slack bot can’t.”
  • “Nothing is shown before it is stored.”
  • “The screen is a window onto the database, not onto the process.”
  • “Durability can’t make a side effect happen exactly once. It can tell you exactly which one is in doubt.”
  • “Recovery stopped being a feature and became a consequence.”
  • “Durability is the easy half. The hard half is Esc.”
  • “A subagent is not a feature. It is a conversation owned by a tool call.”
  • “Conversations remember names, not code. That is why you can change the code.”

What to leave out

Documents and fork semantics, code mode’s deterministic replay, the details of compaction thresholds, storage backends beyond a single mention, hook chains, the task graph. Each is interesting; none survives a ten-minute cut. Keep them for questions. Code mode’s journal (chapter 13) is a particularly good answer to “what about long-running scripts?”

Likely questions

QuestionShort answer
Isn’t this just Temporal for agents?Same family of idea (durable execution), different trade-offs: no separate server, runs inside your process or a Durable Object, and the unit is a conversation with a transcript, not a workflow function. The transcript and app state live in the same commits as the tasks.
Exactly-once tool calls?No. Intent is committed before the effect; after a crash, replay-safe tools rerun and others are reported as interrupted to the model. External effects need idempotency keys.
What does it cost?A commit per visible change, throttled (100 ms for streaming by default). On local SQLite this is cheap; remote storage can commit less often.
Multiple servers?One process owns a storage at a time. Scale by sharding sessions, as the Durable Object example does (one object per session).
Why TypeScript?Easiest way to bootstrap; runs everywhere there is JavaScript. A port is not ruled out.
Will Pi the coding agent move to it?Pi Durable does not replace it. Lessons flow back as they prove themselves.

Things to resolve before the talk

Appendix A

Glossary

TermMeaning
Abort handlerThe code a task runs once when aborted, after everything it owns has finished; decides the aborted outcome and cleans up its own effects.
Active transcriptThe entries from the newest head to the tail; what the model sees.
AgentWhat a conversation runs with: model, thinking level, extensions, tools, instructions, working directory. Stored as names in pi.agent.
Background taskA conversation-owned task outside the conversation’s current work. Esc does not reach it; the conversation can be idle while it runs.
BoundaryA point between turns where queued submissions can safely be placed.
CheckpointA task’s stored progress: the next phase and its data.
CommitOne atomic write of entries, documents, tasks and submissions.
CompactionA task that summarizes older messages and places a headed summary entry.
CompletingA task that has decided its outcome but still owns live work; it becomes terminal once that drains.
ConversationA transcript scope. May fork another at an entry; may be owned by a task.
DocumentTyped, mutable JSON state committed with entries; scoped to session, conversation, or task.
Effect sandwichCommit intent, perform the effect, commit the outcome.
EntryAn immutable transcript record.
EnvironmentWhere tools touch files and processes; built per call.
ExtensionA named bundle of sections, tools, hooks, wraps and tasks.
ForkA conversation that sees its parent’s history up to an entry, without copying.
GenerationThe built-in task for one model request (pi.generation).
HeadA marker on an entry saying where the model’s context starts.
HookExtension code that steps into a built-in task (before a request, before a tool…).
InboxThe queue of submissions waiting for a boundary (pi.inbox).
MemoA small first-writer-wins value stored with a task, for decisions made once.
Mutation lineThe single serialized path all commits take.
OrphanedAn aborted task whose code was unavailable, so no cleanup ran.
RegistryThe extensions this process installed; can change while running.
Replay safeA tool that may simply run again after a crash interrupted it.
Request IDA caller-chosen key that makes a submission exactly-once.
Run / turnA turn is one model response and its tool calls; a run is the turns from an input to its answer.
SessionThe transactional core under a harness: one storage, one mutation line.
Steer / follow-upInput placed after the current tool round / after the run answers.
SubmissionInput or a write handed to a conversation; queued, placed, done or unanswered.
TaskA durable state machine: input, checkpoint, phases, abort handler, owner.
View / watchA conversation’s committed state for UIs; a watch delivers each commit’s exact operations.
