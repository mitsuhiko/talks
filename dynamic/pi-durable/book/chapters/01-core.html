Part II

How it works

One rule, five kinds of records, and one kind of worker. Almost every feature of Pi Durable falls out of these.

Chapter 5

The one rule: commit before you show

If you remember one thing about Pi Durable, remember this: nothing is visible until it is stored. Not a streamed token, not a line of tool output, not a queued message. Everything else is built on that rule.

The mutation line

A harness opens over one storage. Inside it, a Session owns a single mutation line: a serialized queue through which every change passes. A change is a commit: a function that, in one transaction, may append transcript entries, change documents, create tasks, and record submissions. Either all of it is stored, or none of it is.

Two consequences follow immediately:

  • Effects never run inside a transaction. A commit cannot wait on a model, a process or a human. This keeps commits short and makes the boundaries between “decided” and “done” explicit.
  • There is no volatile path to the screen. A streaming answer is committed as a partial at most every 100 milliseconds. A tool’s running output is committed the same way. A UI sees them because they are in storage, not because the process told it.

Why this one rule buys so much

PropertyWhy it follows
A crash loses almost nothingWhatever anyone saw was stored. At most the last throttle window of streaming (100 ms by default) is gone.
Recovery is just reopeningThe new process reads the same state the old one was showing. There is no second copy to reconcile.
Any number of viewersA UI is a reader of committed state. Ten UIs, or one that joins late, all read the same thing.
Consistency between partsA tool’s result entry and the todo list it updated are in the same commit. They can never disagree.
Memory is a cacheThe process keeps a working set in memory. Anything not in use can be dropped and reloaded.
An analogy

The screen is a window onto the database, not onto the process. When the process dies, the window does not go dark: it just stops changing until a new process takes over the same database.

The price

Every visible change costs a commit. Partials are throttled so this stays cheap on local SQLite; a host with remote storage can commit less often (say every 500 ms). And one process owns a storage at a time: there is no cross-process locking. Other clients attach to that process.

Chapter 6

What lives in storage

Storage holds four tables of records and one kind of mutable state. That is the entire durable model. If you can draw this page, you understand what survives a crash.

The four tables

Conversations are transcript scopes. A conversation has two optional edges: a parent (it was forked from that conversation at a given entry) and an owner (a task created it, as a subagent). These two edges are deliberately separate: one is about history, the other about responsibility.

Entries are the transcript. They are immutable, their IDs are ordered across the whole session and never reused. Built-in kinds are user messages, model answers, tool results, system prompt changes, resets and compaction summaries. Applications add their own kinds, for example a chat mention that shows who asked.

Tasks are units of work with a stored checkpoint. They are the subject of the next chapter.

Submissions are what someone handed to a conversation: user input (which asks the model something) or a write (an entry to append without asking anything). A submission moves from queued to placed to done, or ends unanswered with a reason. An optional requestId makes it exactly-once: submit the same request ID again, after a crash or a network retry, and you get the original submission back.

Documents: the part that changes

Entries never change, but some things obviously do: the model selected for a conversation, the output of the tool that is running right now, the queue of messages typed while the agent was busy, the money spent. These live in documents: typed JSON values stored next to the transcript and changed in the same commits. Under the hood, a document change is recorded as a small list of JSON operations (via Chord, Earendil’s replicated-state library), with an occasional full copy so that replay stays short.

The built-in documents are worth knowing by name, because they are what makes “what is happening right now” durable:

DocumentHolds
pi.agentWhat this conversation runs with: model, thinking level, selected extensions and tools (as names), instructions, working directory.
pi.liveThe run in progress: the streaming partial answer, retry backoff, every running tool call with its output so far, nested calls, compactions in flight.
pi.inboxSubmissions waiting for a turn boundary: steers, follow-ups, writes.
pi.usageTokens and cost, per model and per tool, including failed and aborted attempts.
pi.providerA stable ID given to the model provider, so prompt caches keep working across restarts.

Documents also have a lifetime: session documents live forever, conversation documents belong to a conversation, and task documents disappear when their task finishes. And conversation documents declare what a fork sees: the value at the fork point, the current value, or a fresh one. That is a product decision, not an optimization (chapter 14).

The storage itself

The storage interface is small. Pi Durable ships four backends and a conformance suite plus benchmarks for writing your own (a key-value store or Postgres would do):

BackendNotes
MemoryNothing persisted. Tests and throwaway agents.
SQLiteOne file. Keeps only the working set in memory: active transcripts, live tasks, pending submissions. The choice for long-running agents.
JSONLAppend-only files in a directory. Keeps the whole history in memory.
Durable ObjectThe SQLite storage of one Cloudflare Durable Object.

The SQLite and JSONL cores use no Node APIs, so with a small adapter they run on Bun or inside a Durable Object. Because active transcripts are bounded by the model’s context window (compaction sees to that), even a conversation with tens of thousands of messages keeps a small memory footprint on SQLite.

Chapter 7

Tasks: work as durable state machines

Everything the harness runs is a task: each request to the model, each tool call, each compaction. Extensions bring their own. A task is a small state machine whose current state is a row in storage, so a process that has never seen it before can pick it up.

The shape of a task

A task definition has a name and a version, a set of named phases, and an abort handler. A task record stores its input and a checkpoint: which phase is next, plus whatever that phase needs. A phase runs some code and ends by committing one of three things:

  • a new checkpoint (“next, do phase B with this data”),
  • a wait (“resume at phase C once these other tasks are done”), or
  • an outcome (completed, failed, aborted).

Two scheduler rules make this robust:

  • A phase must make durable progress. If a phase returns without having changed its checkpoint or committed an outcome, the task is faulted. Progress that is not written down does not count.
  • On reopen, running becomes pending. Waiting tasks stay waiting. Nothing else happens at open; the scheduler later reserves pending tasks like any others and runs the phase in their checkpoint. There is no separate recovery code path per feature.

The effect sandwich

This is the most important idea in the task model, and the most honest one. Durability cannot make an external effect happen exactly once: if the process dies while a card is being charged, nobody knows whether the bank saw the request. What durability can do is make that uncertainty explicit and local:

A task that restarts in the middle knows precisely which effect is in doubt, and decides: retry safely with an idempotency key, poll an external handle (“is job 42 done?”), or report the interruption to whoever can decide. Tool calls use exactly this (chapter 8): a tool marked replay safe is simply run again; any other tool is reported to the model as interrupted, never repeated.

Memos: decisions you only make once

Sometimes a step has to decide something that must not be decided twice: an approval asked in Slack, a random choice, a generated name. A memo is a small value stored with the task where the first write wins. A hook that asks a human for approval stores the answer in a memo; after a restart it finds the stored answer instead of asking again.

Time, versions, and missing code

  • Timers survive restarts. A task sleeps until a wall-clock time stored in its checkpoint. A retry backoff is “retry at 14:02:10”, not “in five seconds”. A reminder that fires tomorrow is a task asleep until tomorrow.
  • Tasks are versioned. A new definition can migrate old checkpoints when it reserves them.
  • Missing code blocks, never destroys. If a task’s extension is not installed (yet), the task stays pending and is reconsidered when the registry changes. The harness never marks work failed just because the code to run it is temporarily missing.
For the talk

“Durability can’t make a side effect happen exactly once. What it can do is tell you, after a crash, exactly which effect is in doubt.”

Chapter 8

One turn, taken apart

With the vocabulary in place, here is what actually happens when you ask an agent something. One answered question is a small tree of tasks, and every arrow below is a commit.

Step by step

  1. Admission. submit() durably records the input. If the conversation is idle it is placed at once as a pi.user entry, and a generation task is created. pi.live.run now says the conversation is busy and which task holds the run.
  2. Prepare. The generation resolves the conversation’s agent, renders the system prompt sections, and compares them with what the transcript says the model last saw. If anything changed, it appends a pi.system entry with only the difference. It checks whether the context is getting too long (chapter 12), then commits its next checkpoint: request, pinned to a model, a thinking level, and the last entry to include.
  3. Request. The model streams. Every 100 ms or so, the partial answer is committed to pi.live. That is how every attached UI sees tokens appear.
  4. Tool round. The response asks for three tools. One commit appends the answer, creates three pi.tool tasks owned by the generation, and puts the generation into waiting on them.
  5. Each tool. A tool task validates the arguments and runs the beforeTool hooks (which may rewrite or block the call). Then it commits its intent: the final arguments and whether the tool is replay safe. Then it executes, streaming output into pi.live. Then it commits the pi.tool-result entry and finishes.
  6. Boundary. When all three are terminal, the generation wakes up in its tools phase. This is a turn boundary: queued steering messages are placed here. It creates the next generation and hands it the run.
  7. Answer. The second generation’s answer has no tool calls. One commit appends it, marks the submission done, and clears the run. The conversation is idle.

Where can it die, and what happens then?

The process dies…On reopen
after submit() returnedThe input is stored. It is placed and answered as usual. A client that resubmits with the same requestId gets the same submission back, not a second question.
while the model streamsThe committed partial is kept in the transcript as an aborted answer (visible, never sent to the model again). The same request is sent again, with the same pinned model and messages.
during a retry backoffThe generation sleeps until the stored deadline, then retries.
while a tool runsReplay-safe tool: it runs again with the stored arguments. Otherwise: an interrupted error result, with the output stored so far, goes to the model, which decides what to do.
while the generation waitsIt is still waiting; it resumes when its tools are done. Nothing to do.
in a subagentThe subagent is a conversation like any other; its own tasks resume (chapter 10).
Why one task per request

Splitting a run into a fresh generation task per model request, and a task per tool call, is what makes all of the above uniform. Each piece has its own checkpoint, so recovery is always local: continue this request, rerun this tool. The run itself is just a pointer in pi.live, handed from one generation to the next.

Chapter 9

One ownership tree

Durability answers “what happens after a crash”. Ownership answers the other hard question of long-running agents: “what happens when someone presses Esc?” In Pi Durable, all tasks and conversations form one tree, and that tree decides what an abort reaches and when something is finished.

The rules

  • Everything names its owner. A task is owned by its conversation or by another task. A conversation is ownerless or owned by a task. A subagent is simply a conversation owned by the tool call that started it.
  • Abort flows down. Aborting something aborts what it owns.
  • Cleanup runs bottom-up. A task’s abort handler starts only after everything it owns has finished. So each task cleans up its own effects, and a parent’s handler sees the final outcome of its children.
  • Owned work does not outlive its owner’s finish. A task that decides its outcome while its children still run is held as completing until they drain. When a tool call returns, its subagent is really done.
  • Background is a boundary. A background task belongs to the conversation but not to its current work. The conversation goes idle while it runs, and Esc leaves it alone. Aborting the task itself, or the conversation with { background: true }, still stops it.

Waiting together

A task can create children and then wait for them without running any code. With allSettled it resumes when all are done. With failFast, the first failure aborts the others. Chapter 19 uses this for a checkout that charges several cards at once and refunds them all if one is declined.

Aborted versus orphaned

There is a fine but important distinction in the outcomes. Aborted means the task’s own abort handler ran and cleaned up. Orphaned means its code was not available (its extension was uninstalled, say) and someone aborted it anyway: no cleanup ran, and effects it started may remain. The harness never pretends cleanup happened.

For the talk

“Durability is the easy half. The hard half is Esc. When you press it, what stops? In Pi Durable, the answer is a tree, and cleanup runs from the leaves up.”
